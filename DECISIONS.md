# DECISIONS.md — bitchat (Wi-Fi LAN transport)

Short record of the decisions taken while adding the Wi-Fi LAN transport to
the iOS/macOS fork. No secrets live in this file.

## D1 — The unit tests use swift-testing, not XCTest

The repository's test target already contains 180 files using
`import Testing` (`@Test` / `#expect`) and only a handful of legacy XCTest
files. The new tests follow the dominant convention so they read like the
rest of the suite. The test target, the runner and the CI job are the same
in both cases, so nothing about the "existing test target" requirement
changes.

## D2 — The LAN transport owns its own `NoiseEncryptionService`

`NoiseEncryptionService` loads the static identity key from the keychain,
so a second instance has the **same** identity: the peer ID and the
fingerprint are identical to the BLE mesh ones (one identity across
transports). It also owns its **own** `NoiseSessionManager`, so a Noise
session established over BLE is never reused over Wi-Fi — a Noise transport
cipher belongs to exactly one physical link. Sharing the BLE instance would
have mixed two links' cipher state under one peer ID.

Consequence: a panic wipe (which rotates the keychain identity) leaves the
LAN transport with a stale in-memory identity. v1 therefore does not run the
LAN transport across a panic reset; this is documented in
`docs/WIFI_TRANSPORT.md` ("Security limits") and is a known follow-up.

## D3 — The transport is always constructed, but inert while the flag is off

`ChatViewModelServiceBundle` always creates the `LANTransport` and adds it
to the router and to the unified peer list. The feature flag
(`bitchat.lan.enabled`, default `false`) is checked inside
`startServices()`: with the flag off the transport opens no listener, starts
no browser and triggers no local-network permission prompt.

The alternative — creating the transport only when the flag is on — would
mean the flag is read once at launch and could never be switched on during
a session. Constructing it unconditionally keeps the wiring static and
makes a runtime settings toggle a small follow-up.

## D4 — The Bonjour service name carries the peer ID

`bitchat-<peer id>` with the peer ID being the 16 hex characters the BLE
mesh already uses. It is a linkable identifier (the BLE announce exposes
the same material in cleartext), it lets the browser skip foreign services
without a round trip, and it avoids a TXT record (whose size is limited
and whose format differs between platforms).

The advertised name is not trusted: the peer ID in the name is only a
routing hint. The identity is proven by the signed hello plus the Noise
handshake.

## D5 — The client always drives the Noise handshake

The side that opened the TCP connection sends the hello first and starts
the Noise handshake; the responder answers. A deterministic rule (for
example "the smaller peer ID initiates") would also work, but the
connection role is already known and needs no extra state, and it removes
the crossed-initiation case entirely.

## D6 — The milestone board was rewritten to the task plan

`MILESTONES.json` was generated by `mox` with a generic three-milestone
scaffold. The task specifies a five-milestone plan with concrete
sub-todos, so the board was rewritten in the same schema (version 1) before
the work started; all progress afterwards was recorded with
`mox milestone …`, never by hand.

## D7 — No test could be executed locally

This workstation is Linux and the VPS is Linux: there is no Swift
toolchain, no Xcode and no Apple simulator, and installing them is out of
scope. The **only** executable check is the macOS CI
(`.github/workflows/swift-tests.yml`), which runs `swift build
--build-tests`, the unit tests, the iOS simulator test job, SwiftLint and
the universal Release builds.

Consequence for the TDD cycle: the "failing test" step was verified by
construction (the test commits reference symbols that the next commit
introduces) and by the CI run on the feature branch, not by a local red
run. This is recorded here as required by the project rules.
